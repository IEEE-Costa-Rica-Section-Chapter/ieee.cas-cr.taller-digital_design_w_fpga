1.2.1

A module is a box with wires

~2 min

A SystemVerilog file describes hardware blocks. One block is one module. It has ports (the wires that go in and out) and a body that says how the outputs depend on the inputs. This is the smallest useful module, an inverter:

inv.sv
module inv (
    input  logic a,      // a wire coming in
    output logic y       // a wire going out
);
    assign y = ~a;       // y is always the opposite of a
endmodule
  • input and output give the direction of each port; logic is the type: one wire (a bit).
  • assign y = ~a; is not an instruction that runs once. It is a permanent connection: whenever a changes, y follows. That is why a hardware description is not a program.
Predict first: what is y when a is 0?
It is 1. The inverter output is always the opposite of its input, at every moment.

1.2.2

One gate at a time

~2 min

The four basic operators work on single bits exactly like the gates you know:

gates4.sv
module gates4 (
    input  logic a, b,
    output logic y_and, y_or, y_xor, y_nand
);
    assign y_and  = a & b;       // AND
    assign y_or   = a | b;       // OR
    assign y_xor  = a ^ b;       // XOR
    assign y_nand = ~(a & b);    // NAND = NOT of AND
endmodule

Note that a, b on one line is allowed: both are inputs. Each assign is its own gate and all of them work at the same time; their order in the file does not matter.

Predict first: with a = 1 and b = 1, what are the four outputs?
y_and = 1, y_or = 1, y_xor = 0, y_nand = 0.

1.2.3

Combining gates and internal wires

~2 min

An expression can combine several gates. When it gets long, name the pieces with internal logic signals (declared inside the module, with no direction):

majority3.sv
module majority3 (
    input  logic a, b, c,
    output logic y             // 1 when at least two inputs are 1
);
    logic ab, ac, bc;          // internal wires: no direction, not ports

    assign ab = a & b;
    assign ac = a & c;
    assign bc = b & c;
    assign y  = ab | ac | bc;  // same as (a&b) | (a&c) | (b&c)
endmodule

It is the same circuit whether you write one long expression or use internal wires. Use wires when it makes the code easier to read.

Predict first: with a = 1, b = 0, c = 1, what is y?
ac = 1, so y = 1. Two of the three inputs are 1.

1.2.4

Vectors: several bits under one name

~2 min

A vector groups bits: logic [3:0] x is four wires, numbered 3 (leftmost, most significant) down to 0. You can use one bit with x[1], or the whole vector at once. The bitwise operators then act bit by bit:

vectors.sv
module vec_demo (
    input  logic [3:0] x, z,
    output logic [3:0] y_and,      // 4 AND gates, one per bit
    output logic       lsb         // a single bit of x
);
    assign y_and = x & z;          // y_and[i] = x[i] & z[i], for i = 0..3
    assign lsb   = x[0];           // bit 0, the rightmost
endmodule
Predict first: x = 4'b1100, z = 4'b1010. What is x & z?
Bit by bit: 1&1, 1&0, 0&1, 0&0 gives 4'b1000.
Check yourself

Constants (literals) and widths

~2 min

A constant is written size'base value: the number of bits, a letter for the base, then the digits. Always give the size, otherwise the tool guesses 32 bits.

1.2.6

Slices, concatenation and replication

~2 min

Three ways to rearrange bits. Suppose a = 4'b1010:

slices.sv
// a = 4'b1010   (bit3=1, bit2=0, bit1=1, bit0=0)

// a[2:1]          slice: bits 2 down to 1     -> 2'b01
// {a[0], a[3]}    concatenation: join, first item on the LEFT -> 2'b01
// {2'b10, 3'b011} the same idea with literals -> 5'b10011
// {4{1'b1}}       replication: repeat 4 times -> 4'b1111

Concatenation is how you build a wider vector from pieces; the width of the result is the sum of the widths.

Predict first: what is {a[1:0], a[3:2]}?
a[1:0] is 2'b10 and a[3:2] is 2'b10, so the result is 4'b1010.

1.2.7

Reduction operators and comparisons

~2 min

Putting an operator in front of a vector combines all its bits into one bit (a reduction). Comparisons also give one bit.

ExpressionMeaningWith x = 4'b1110
&x1 if all bits are 10
|x1 if any bit is 11
^xXOR of all bits: the parity (1 if an odd number of ones)1
x == 4'd141 if equal1

Also available: !=, <, >. They cost more hardware than simple gates (a comparison can use carry cells). The logical operators &&, || and ! treat a whole value as true/false; use them in conditions, and use & | ^ ~ to combine bits.

Predict first: what is ^4'b0110?
Two ones (an even number), so the parity is 0.

1.2.8

Arithmetic and the ? : multiplexer

~2 min

+ and - work on vectors, and the tool builds an adder. The result is only as wide as the signals involved, so an unwidened carry is lost:

arith.sv
logic [3:0] a, b;          // each 0..15
logic [3:0] sum4;
logic [4:0] sum5;

assign sum4 = a + b;                    // 9 + 8 -> 17 does not fit: result is 1 (carry lost)
assign sum5 = {1'b0, a} + {1'b0, b};    // widen first: 9 + 8 -> 17 (5'b10001)

The conditional operator is a 2-way multiplexer:

mux2.sv
module mux2 (
    input  logic       sel,
    input  logic [3:0] d0, d1,
    output logic [3:0] y
);
    assign y = sel ? d1 : d0;     // sel = 1 picks d1, sel = 0 picks d0
endmodule

It is one multiplexer in hardware, not a branch that is "taken": both inputs are always present and sel chooses.

Predict first: what are sum4 and sum5 for a = 4'd9, b = 4'd8?
sum4 = 4'd1 (17 mod 16) and sum5 = 5'd17.
Check yourself
1.2.9

Choices with always_comb

~2 min

For anything more than an expression, use a procedural block. For combinational logic, always write always_comb: inside it you can use if/else, and signals are assigned with a plain =. The same multiplexer:

mux2b.sv
module mux2b (
    input  logic       sel,
    input  logic [3:0] d0, d1,
    output logic [3:0] y
);
    always_comb begin
        if (sel) y = d1;
        else     y = d0;
    end
endmodule

This is the same circuit as the ? : version. always_comb is not a loop that runs: it re-describes the output every time an input changes. The block ends with end, and there are two rules for now:

  • Assign outputs of the block with = (not <=; that is for flip-flops, in module 1.4).
  • The output must get a value in every branch. Here the else guarantees it.
Predict first: what would the output do if the else line were missing?
When sel = 0 the block says nothing about y, so y would have to keep its old value. That is a memory, not a gate. The next step is about exactly this.
Check yourself
1.2.10

case, and the rule that prevents latches

~2 min

When there are many options, use case. Give it a default so that every value is covered:

mux4.sv
module mux4 (
    input  logic [3:0] d0, d1, d2, d3,
    input  logic [1:0] sel,
    output logic [3:0] y
);
    always_comb begin
        case (sel)
            2'd0:    y = d0;
            2'd1:    y = d1;
            2'd2:    y = d2;
            default: y = d3;     // covers sel = 3 (and unknown values in simulation)
        endcase
    end
endmodule
⚠️
The rule that prevents latches

Inside always_comb, every output must get a value in every branch. If one branch does not assign it, the output would have to remember its old value: a latch, a memory that the FPGA logic cells do not offer. Give every case a default and every if an else. In lab 1.2b you will provoke the error on purpose.

Predict first: this case has branches for sel = 0, 1, 2 and no default. Which input value is the problem?
sel = 3: nothing says what y is then.
Check yourself
1.2.11

Parameters and using a module inside another

~3 min

A parameter is a constant chosen when the module is used, so one description serves many sizes. Here the multiplexer width is configurable:

mux2w.sv
module mux2w #(
    parameter int W = 4                 // default width: 4 bits
) (
    input  logic         sel,
    input  logic [W-1:0] d0, d1,
    output logic [W-1:0] y
);
    assign y = sel ? d1 : d0;
endmodule

To use it (instantiate it) inside another module, give it an instance name and connect each port by name:

top_fragment.sv
logic [7:0] a, b, out;
logic       s;

mux2w #(.W(8)) u_mux (      // W = 8 for this instance; u_mux is its name
    .sel(s),                // .port_name(signal_here)
    .d0 (a),
    .d1 (b),
    .y  (out)
);

Named connections are safer than relying on the order of the ports: if someone adds a port later, nothing silently moves to the wrong place. Every instance is its own copy of the hardware.

Predict first: how many multiplexer bits does u_mux contain?
8, because W = 8 for that instance.

1.2.13

Checking a design: the smallest testbench

~3 min

Before spending minutes on a build, simulate. A testbench is a module with no ports: it creates the inputs, instantiates your design (the device under test, DUT) and checks the outputs. The smallest one, for the inverter of step 1.2.1:

tb/inv_tb.sv
`timescale 1ns/1ps
module inv_tb;
    logic a, y;                      // signals we drive and observe

    inv dut (.a(a), .y(y));          // the design under test

    initial begin                    // runs once, from time 0
        a = 0;  #1;                  // drive a = 0, wait 1 ns
        if (y !== 1) $fatal(1, "inv: a=0 gave y=%b, expected 1", y);

        a = 1;  #1;
        if (y !== 0) $fatal(1, "inv: a=1 gave y=%b, expected 0", y);

        $display("PASS");            // reached only if every check passed
        $finish;
    end
endmodule
  • The testbench is simulation-only code: delays like #1, initial, $display and $fatal exist only here. It never goes to the FPGA.
  • !== is a strict comparison that also catches unknown values (x).
  • It ends in one of two ways: it prints PASS, or $fatal stops it with a message and make sim reports an error.
Predict first: which line of the testbench is never reached if the DUT is wrong?
$display("PASS"): the $fatal before it stops the simulation first.

1.2.14

Exhaustive testing and reading failures

~3 min

With few inputs you can try all of them. This is the testbench of the first lab (three inputs, so 8 combinations) with a for loop:

tb/gates_tb.sv
// gates_tb.sv - exhaustive self-checking testbench: all 8 input combinations.
// The reference is written in a different style (counting ones) on purpose.
`timescale 1ns/1ps
module gates_tb;
    logic [2:0] x;
    logic maj, parity, all_equal;

    gates dut (.x(x), .maj(maj), .parity(parity), .all_equal(all_equal));

    initial begin
        for (int i = 0; i < 8; i++) begin
            int ones;
            x = i[2:0];
            #1;
            ones = $countones(x);
            if (maj !== (ones >= 2))
                $fatal(1, "maj wrong for x=%b: got %b, expected %b", x, maj, ones >= 2);
            if (parity !== (ones % 2 == 1))
                $fatal(1, "parity wrong for x=%b: got %b, expected %b", x, parity, ones % 2 == 1);
            if (all_equal !== (ones == 0 || ones == 3))
                $fatal(1, "all_equal wrong for x=%b: got %b, expected %b", x, all_equal, ones == 0 || ones == 3);
        end
        $display("PASS");
        $finish;
    end
endmodule

Two ideas to take from it:

  • Exhaustive: every input combination is checked, so there is no doubt left when it passes.
  • The reference is written differently from the design. The expected value comes from counting ones, while the design uses AND/OR. If both were written the same way, the same mistake would be copied to both and nothing would be detected.

The commands (run them inside a lab folder):

VSCode terminal
make sim                 # run every testbench of the lab
make sim TB=gates        # only tb/gates_tb.sv
make wave TB=gates       # open the waveform of that run (Surfer)

When a testbench fails, the message looks like this (with the unsolved lab 1.2a):

make sim
FATAL: tb/gates_tb.sv:21: all_equal wrong for x=000: got 0, expected 1

It gives the file and line of the check, the input that failed, what your design produced and what was expected. Read it before touching the code.

Lab 1.2b: a latch by mistake

~6 min

Open 1-Basic/labs/latch. The file src/dec2.sv is a 2-to-4 decoder with one case missing:

src/dec2.sv (buggy)
// dec2.sv - LAB 1.2b: a 2-to-4 decoder with a bug (one case is missing).
//
//   s = 0 -> y = 0001     s = 1 -> y = 0010
//   s = 2 -> y = 0100     s = 3 -> y = 1000
//
// 1. Run `make stat TOP=dec2` and read the error.
// 2. Run `make sim` and read that failure too.
// 3. Fix the module and run both again.
module dec2 (
    input  logic [1:0] s,
    output logic [3:0] y
);
    always_comb begin
        case (s)
            2'd0: y = 4'b0001;
            2'd1: y = 4'b0010;
            2'd2: y = 4'b0100;
            // the case s = 3 is not described here
        endcase
    end
endmodule
  1. Ask the synthesizer. make stat runs only synthesis (no board pins needed) on any module:
    VSCode terminal
    make stat TOP=dec2
    what Yosys says (excerpt)
    ERROR: Latch inferred for signal `\dec2.\y [2:0]' from always_comb process ...
    Yosys refuses: y would have to remember its value when s = 3.
  2. Now simulate: make sim. The testbench catches the same bug from the other side (the output keeps the old value):
    make sim
    FATAL: tb/dec2_tb.sv:14: s=3: got y=0100, expected 1000
  3. Fix the module (add the missing case or a default) and repeat both commands until they succeed, then make prog: the LEDs show the decoder output as s counts 0, 1, 2, 3.

Extra (read-only experiment): change always_comb to always @* in the buggy version and run make stat TOP=dec2 again. This Yosys version also stops, but with a less helpful message (“D latches are not supported”). always_comb tells the tool what you meant, so the error names the real problem.
