From state diagram to code

~8 min

A finite-state machine is a register holding the current state plus combinational logic that computes the next state and the outputs. In a Moore machine the outputs depend only on the state; in a Mealy machine they also depend on the current input (faster to react, but the output can glitch with the input). This module uses Moore.

Always write it in the two-process style, which keeps the three parts of the hardware visible:

fsm_template.sv
typedef enum logic [1:0] { S_A, S_B, S_C } state_t;   // names instead of magic numbers
state_t state, next;

// process 1: the state register (the only sequential part)
always_ff @(posedge clk or negedge rst_n)
    if (!rst_n) state <= S_A;
    else        state <= next;

// process 2: next state from (state, inputs). Pure combinational logic.
always_comb begin
    next = state;                       // default: stay. Prevents latches and shortens the code
    case (state)
        S_A: if (go) next = S_B;
        S_B: next = S_C;
        S_C: if (go) next = S_A;
        default: next = S_A;            // unreachable states fall back to a safe state
    endcase
end

// outputs (Moore: from the state only)
assign busy = (state != S_A);

Procedure: (1) list what the machine must remember → those are the states; (2) draw the diagram with one arrow per input value for every state; (3) copy the arrows into the case; (4) derive the outputs from the states.

~15 min

Open 1-Basic/labs/seq-detector. Draw the diagram on paper first, then fill the case in src/seq_detect.sv. The state register and the output are already written.

src/seq_detect.sv (your work)
// seq_detect.sv - LAB 1.5: a Moore state machine that detects the bit sequence 1011.
//
//   * One bit arrives per clock cycle on `in`.
//   * detect = 1 while the machine is in the state "I have just seen 1011".
//   * Matches may OVERLAP: in 1011011 the sequence is found twice.
//   * rst_n (asynchronous, active low) returns to S_IDLE.
//
// Draw the state diagram on paper first (5 states: nothing, 1, 10, 101, 1011).
// Then fill in the transitions in the always_comb block, TWO-PROCESS style:
//   always_ff   : the state register (provided)
//   always_comb : next state from (state, in)  <-- your work
//   assign      : the output from the state     (provided, Moore)
module seq_detect (
    input  logic clk,
    input  logic rst_n,
    input  logic in,
    output logic detect
);
    typedef enum logic [2:0] {
        S_IDLE,     // nothing useful seen
        S_1,        // seen ...1
        S_10,       // seen ...10
        S_101,      // seen ...101
        S_1011      // seen 1011: detect
    } state_t;

    state_t state, next;

    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n) state <= S_IDLE;
        else        state <= next;
    end

    always_comb begin
        next = state;                       // default: stay
        case (state)
            // TODO: one line per state: where do we go when in = 0 and when in = 1?
            default: next = S_IDLE;
        endcase
    end

    assign detect = (state == S_1011);
endmodule

The testbench (tb/seq_detect_tb.sv) checks directed cases (including overlaps and near misses), then 4000 random bits against a reference model: a 4-bit shift register compared with 1011. It also resets the machine in the middle of a match.

On the board

make prog: a 16-bit pattern is played at 2 bits per second (the pattern generator and a tick generator are provided; the tick_gen is the reference one from module 1.4). LED0 = current input bit, LED1 = detect, LED2–LED5 = the last four bits (newest on LED2, so LED5 holds the oldest). When LED5, LED4, LED3, LED2 read 1 0 1 1 (lit, dark, lit, lit), LED1 must light.

📝
The detect LED lasts a whole tick

The machine samples the input every clock cycle, but the pattern changes every half second, so the same bit is seen millions of times. Consecutive identical bits just keep the machine in place: that is why it works at any speed, as long as the input is stable around the clock edge.
