Module 0 Setup · common to all levels

Configuration

Set up your workstation and run your first design on the Tang Nano 20K.

By the end of this module you can

  • Install the open-source FPGA toolchain (OSS CAD Suite) and VSCode
  • Create a project from the course template and check your tools with one command
  • Simulate a design, then synthesize, place & route and program it on the board
  • Explain what each tool in the flow does and read the key lines of its report
Time
45–60 min
Disk
~2 GB
Board
Tang Nano 20K
Language
SystemVerilog

What you need

  • A Sipeed Tang Nano 20K and a USB-C cable that carries data (many charge-only cables do not work).
  • A computer with Windows 10/11 (the path this module follows first), Linux, or macOS. Administrator rights are needed only for the USB driver on Windows.
  • GNU make, a small build tool (step 0.1 shows the one-line install for each system).
  • No other hardware: every lab in the course uses only what is on the board.
📝
How this module works

Work through the steps in order. Tick each checklist item when it is truly done; your progress is saved in this browser. The module is complete when every item is ticked and the quiz is passed.

0.1

Install the OSS CAD Suite

~15 min

The OSS CAD Suite is one download that bundles everything we use: Yosys (synthesis), nextpnr (place & route), Apicula’s gowin_pack (bitstream), openFPGALoader (programming), Icarus Verilog (simulation) and the Surfer / GTKWave waveform viewers.

Fastest way: run the setup script

The course repository includes a script for each system. It installs what is missing (suite, make, VSCode extensions), is safe to run again, never edits your PATH, and finishes by testing a copy of the project template (make doctor, make sim, make build). Run it from the root of the course repository:

Windows (PowerShell) 
powershell -ExecutionPolicy Bypass -File 0-Configuration\scripts\setup-windows.ps1
WSL (inside Ubuntu) 
bash 0-Configuration/scripts/setup-wsl.sh
Linux 
bash 0-Configuration/scripts/setup-linux.sh
macOS 
bash 0-Configuration/scripts/setup-macos.sh

Add --dry-run (-DryRun on Windows) to see what it would do without changing anything, or --check (-Check) to only verify an existing installation. The last lines are a summary: every FAIL must be fixed; WARN lines about the board or the USB driver are normal until you reach step 0.4. If the script finishes with “everything required is OK” you can tick the checklist of this step and the next ones that it covers, then continue at 0.4.

📝
What the scripts have been tested on

The Windows script was run in check mode on Windows 11 and the WSL script on Ubuntu 24.04 (WSL 2). The Linux (native) and macOS paths use the same code but have not been run on those systems yet. On macOS the system make is version 3.81; the course Makefile has only been tested with GNU Make 4.x, so the script warns about it.

== Rules ==
1. Before any step that needs administrator/root rights (sudo, UAC), installs software, or changes a driver, say exactly what it will do and wait for my "yes". Downloading the suite (about 0.7 GB) also needs my approval.
2. Do not edit my PATH, shell profile or registry. The course Makefile finds the suite by itself (OSS_CAD_SUITE, C:/oss-cad-suite, ~/oss-cad-suite, /opt/oss-cad-suite).
3. Do not modify files in this repository. Do all test builds in a temporary COPY of project-template.
4. Never say something works unless you ran the command in this session and read its output. Quote the key output lines. If you could not test something, say "not tested".
5. Do not guess hardware facts. If a step needs board information you do not have, ask me or report it as unknown.
6. Never run `make flash` (it writes the board's permanent flash). Only `make prog` (volatile) and only after I confirm the board is connected.
7. If a command fails, show me the error, diagnose it, and try at most three fixes before asking me. Do not loop.
8. Long commands (the download and unpacking take minutes): run them in the background or with a long timeout and wait. Do not kill them.

== Procedure ==
Step 1 - Look at my system. Report: operating system and version, whether this is native Windows, WSL, Linux or macOS, CPU architecture, free disk space on the drive where the suite will go (need at least 4 GB), and whether internet access works. Confirm that the current folder contains project-template/ and 0-Configuration/scripts/.

Step 2 - Preview. Run the matching setup script in dry-run mode, then summarize in plain words what it would install and where. Ask me to approve.
  Windows : powershell -NoProfile -ExecutionPolicy Bypass -File 0-Configuration\scripts\setup-windows.ps1 -DryRun
  WSL     : bash 0-Configuration/scripts/setup-wsl.sh --dry-run
  Linux   : bash 0-Configuration/scripts/setup-linux.sh --dry-run
  macOS   : bash 0-Configuration/scripts/setup-macos.sh --dry-run
  (If I use WSL, the course tools go INSIDE WSL; VSCode stays on Windows with the "WSL" extension.)

Step 3 - Install. After my approval, run the same command without the dry-run flag. Read the Summary at the end. Every line marked FAIL must be fixed. WARN lines about the board or the USB driver are expected if the board is not connected yet.

Step 4 - Fix failures. Use the script output, step 0.7 of 0-Configuration/index.html and these known causes:
  - "make: command not found": Windows needs `winget install ezwinports.make` and a NEW terminal; Debian/Ubuntu: sudo apt install make; macOS: xcode-select --install.
  - Could not find the download (GitHub API limit or proxy): download oss-cad-suite-<platform>-<date>.tgz by hand from https://github.com/YosysHQ/oss-cad-suite-build/releases/latest and rerun with the environment variable OSS_CAD_URL set to its URL, or unpack it into the suite folder.
  - Windows: keep the suite in a short path without spaces and outside OneDrive (default C:\oss-cad-suite).
  - macOS: if tools are blocked, run xattr -dr com.apple.quarantine ~/oss-cad-suite. The system make is 3.81; if make fails on the Makefile, install GNU make 4 (brew install make) and use gmake.
  - A build that shows "LUT4: 0" and "DFF: 0" means an input of an instantiated module is not connected; this is a design problem, not a setup problem.
Rerun the script after each fix (it is safe to repeat).

Step 5 - Check it yourself (do not only trust the script). In a temporary copy of project-template, run and show me the key output of:
  make doctor      every tool prints a version
  make sim         the testbench prints PASS
  make build       build/top.fs exists (about 4.6 MB); the resource report should show DFF 25, a LUT4 count in the tens (we have seen 47 and 73 with different suite versions) and "PASS at 27.00 MHz"; counts and frequencies vary between tool versions, so do not treat them as errors
  On Windows, `make` may be called mingw32-make; use whichever exists. Then delete the temporary copy.

Step 6 - VSCode. Confirm `code --list-extensions` shows mshr-h.veriloghdl and surfer-project.surfer (for WSL, VSCode runs on Windows: check the "WSL" extension exists and tell me to open the folder with `code .` from the WSL terminal). If `code` is not on the PATH, tell me how to install the command; do not guess.

Step 7 - The board (only if I say it is connected by a USB cable that carries data, and only now). Ask me first.
  - Windows: the board's debug interface needs the WinUSB driver. If `make doctor` or the script reports no usable device, guide me through Zadig by voice, step by step: Options > List All Devices, choose the JTAG interface of the BL616 debugger (interface 0, USB ID 0403:6010), driver WinUSB, Replace Driver. On the verified board the entry is called "USB Debugger (Interface 0)" and must show USB ID 0403 6010; "USB Debugger (Interface 1)" is the serial port and must NOT be changed. The list also contains many unrelated devices, so confirm the ID with me before I click Replace Driver. Do not install drivers without my approval.
  - Linux: the script installs a udev rule; ask me to unplug and replug the board.
  - macOS: no driver is needed.
  - WSL: WSL cannot see USB by itself. It needs usbipd-win on the Windows side (usbipd list, usbipd bind --busid <ID> as administrator, usbipd attach --wsl --busid <ID>). Verified flow: winget install --exact dorssel.usbipd-win, then in an administrator PowerShell usbipd list / bind (add --force if USBPcap is reported) / attach --wsl --busid ; inside WSL install usbutils, check lsusb shows 0403:6010 and run sudo chmod a+rw on its /dev/bus/usb// (sudo needs my password: ask me to run it). While attached, Windows cannot use the board. Do these steps only if I ask, otherwise tell me to program from native Windows.
  Then run `make doctor` and show the USB line, run `make prog` in the temporary copy, and ask me to look at the board and answer:
    a) Does LED0 blink about once per second? (the other five LEDs stay off)
    b) While I hold button S1, does LED0 stay dark, and does it restart blinking when I release S1?
  If (b) is the opposite (LED0 blinks only while S1 is pressed), the button polarity assumption is wrong: tell me, and explain that in project-template/src/top.sv the constant BTN_PRESSED must change from 1'b1 to 1'b0. Do not change repository files yourself; report it so I can.

Step 8 - Final report. Give me a table with one row per check: toolchain installed, make, simulation, build, VSCode extensions, board detected, board programmed, LED0 blinks, S1 reset behaviour. Mark each PASS, FAIL, SKIPPED or NOT TESTED, with the exact tool versions you saw. Then list anything I still must do by hand, in order. Finish with one sentence: whether I am ready to continue with step 0.5 (Hello, FPGA) of Module 0.

  4. Check that the main tool is where it should be (PowerShell):
PowerShell

It must print True.

Install GNU make

The suite does not include make. Install it with winget, then close and reopen VSCode (or your terminal) so the new command is found:

PowerShell 
winget install ezwinports.make
make --version

The last command must print GNU Make and a version number. (With Chocolatey: choco install make.)

💡
No PATH changes needed

You do not need to add the suite to your PATH. The project’s Makefile finds it automatically in C:\oss-cad-suite (or in the folder named by the OSS_CAD_SUITE environment variable) and adds it to the PATH of the commands it runs. This also avoids the suite’s bundled Python shadowing your own.

Download the release matching today’s date from the releases page (replace <date> with the date in the file name, e.g. 20251213) and extract it in your home folder:

Terminal 
cd ~
tar xf oss-cad-suite-linux-x64-<date>.tgz
ls ~/oss-cad-suite/bin/yosys

The project’s Makefile finds ~/oss-cad-suite by itself; no PATH edits are required.

Make sure GNU make is installed:

Terminal 
sudo apt install make        # Debian/Ubuntu/WSL (Fedora: sudo dnf install make)
make --version

0.4

Connect the board

~10 min

The Tang Nano 20K has a single USB-C port wired to an on-board BL616 chip. It acts as two devices at once: interface 0 is the JTAG programmer (this is what we need now) and interface 1 is a serial port to the FPGA (used from Level 2 for UART). It identifies itself as USB ID 0403:6010. Plug the board in, then follow your system:

Windows needs a generic USB driver (WinUSB) on interface 0 so openFPGALoader can talk to it. Use Zadig:

  1. Plug in the board and open Zadig as administrator.
  2. Options → List All Devices.
  3. In the drop-down pick USB Debugger (Interface 0). The list is long (every USB device of the PC is in it), so before replacing anything check that the USB ID fields under it read 0403 and 6010. The entry just below, USB Debugger (Interface 1), is the serial port: do not pick it.
  4. Choose WinUSB as the target driver and click Replace Driver.
⚠
Only interface 0

Leave Interface 1 alone: it is the serial port (a COM port in Device Manager) and we use it later. Replacing the driver on interface 0 also means Gowin’s own Windows programmer will no longer see the board until you restore the original driver from Device Manager.

Allow your user to access the device without sudo with a udev rule:

Terminal 
echo 'SUBSYSTEM=="usb", ATTR{idVendor}=="0403", ATTR{idProduct}=="6010", MODE="0666", TAG+="uaccess"' \
  | sudo tee /etc/udev/rules.d/99-tang-nano.rules
sudo udevadm control --reload-rules && sudo udevadm trigger

Unplug and re-plug the board.

WSL 2: USB passthrough

WSL cannot see USB devices until you share them with usbipd-win. In an administrator PowerShell on Windows (open a new window after installing so that usbipd is on the PATH):

PowerShell (Windows side, administrator) 
winget install --exact dorssel.usbipd-win
usbipd list                                   # find the BUSID of 0403:6010 (“USB Debugger”)
usbipd bind --busid <BUSID>                   # once; add --force if it complains about the USBPcap filter
usbipd attach --wsl --busid <BUSID>           # every time you plug the board in

Then, in WSL, check that the board arrived and give your user access to it:

Ubuntu (WSL) 
sudo apt install -y usbutils
lsusb | grep 0403                                  # 0403:6010 must be listed
ls /dev/bus/usb/001/                               # note the new device number, e.g. 003
sudo chmod a+rw /dev/bus/usb/001/003               # replace 003 with your number
📝
What to expect in WSL
  • The chmod only lasts until the board is detached or re-attached; repeat it (check the number again) every time. The udev rule above makes it permanent only if your WSL has systemd/udev running.
  • While the board is attached to WSL, Windows cannot use it: run usbipd detach --busid <BUSID> to give it back.
  • Without this whole procedure make sim and make build still work in WSL; only make prog needs the board.

0.5

Hello, FPGA: simulate, build, program

~15 min

The template contains a complete design: a counter that toggles an LED every half second, with button S1 as a reset. You will run it three ways: in simulation (no hardware), through the build flow, and on the board. First look at the code. It is short, and you will meet every piece again in Level 1.

src/blink.sv — the design
src/blink.sv 
// blink.sv - toggles `out` every half period of BLINK_HZ.
// Parameterized so the same code runs on the board (27 MHz clock) and
// in simulation (tiny clock so the waveform stays short).
module blink #(
    // input clock frequency
    parameter int CLK_HZ = 27_000_000,
    // desired blink frequency
    parameter int BLINK_HZ = 1
)(
    input logic clk,
    // active-low reset
    input logic rst_n,
    // active-high blink signal
    output logic out
);
    // Clock cycles in half a blink period
    localparam int HALF = CLK_HZ / (BLINK_HZ * 2);
    localparam int CNT_W = $clog2(HALF);

    // Initial values are honored by the Gowin FPGA at configuration time
    logic [CNT_W-1:0] cnt;
    logic q;

    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n) begin
            cnt <= '0;
            q <= 1'b0;
        end else if (cnt == CNT_W'(HALF - 1)) begin
            cnt <= '0;
            q <= ~q;
        end else begin
            cnt <= cnt + 1'b1;
        end
    end

    assign out = q;
endmodule
src/top.sv and the pin constraints — connecting the design to the board (the full .cst explains every line)
src/top.sv 
// top.sv - board-level wrapper for the Tang Nano 20K.
// Port names must match the names in constraints/tang_nano_20k.cst.
module top (
    // 27 MHz oscillator
    input  logic clk,
    // user button S1, used as reset
    input  logic btn_s1,
    // user LEDs, ACTIVE-LOW (0 = lit)
    output logic [5:0] led
);
    // Logic level on btn_s1 while S1 is pressed.
    // The board examples suggest 1 (pressed = high), but this is inferred, not
    // documented: if LED0 blinks ONLY while S1 is held, change it to 1'b0.
    localparam logic BTN_PRESSED = 1'b1;

    // Active-low reset for the design: 0 while S1 is pressed.
    // Note: releasing the button is asynchronous to clk. That is acceptable for
    // a blinker; a proper reset synchronizer comes in Level 1.
    logic rst_n;
    assign rst_n = (btn_s1 != BTN_PRESSED);

    logic blink_out;

    blink #(
        .CLK_HZ(27_000_000),
        .BLINK_HZ(1)
    ) u_blink (
        .clk(clk),
        .rst_n(rst_n),
        .out(blink_out)
    );

    // LED0 follows the blink signal. LED1..5 stay off.
    assign led = ~{5'b00000, blink_out};
endmodule

⚠
Active-low LEDs

The six user LEDs light when the pin is driven low. That is why top.sv inverts the signal with ~: blink_out = 1 becomes led[0] = 0 (lit) and the other five bits stay 1 (off).

📝
Reset button S1 and its polarity

blink has an active-low reset input rst_n: while it is 0 the counter and the output are forced to 0. In top.sv, rst_n is 0 while S1 is pressed. Which logic level S1 produces when pressed is not documented; the Sipeed examples suggest 1, and BTN_PRESSED in top.sv holds that assumption. Step 3 below tests it on your board, and the fix is one character if it is wrong.

The .cst file is documented line by line: open constraints/tang_nano_20k.cst and read it once.

3. Program the board

VSCode terminal 
make prog

Within a second or two, LED0 (the first of the six) blinks once per second: half a second lit, half a second dark. The other five stay off. Now test the reset: while you hold S1, LED0 must stay dark; when you release it, the blinking restarts from the beginning. prog loads the design into the FPGA’s SRAM, so it disappears at power-off. To keep it, use make flash (writes the SPI flash). Prefer prog while developing: it is faster and does not wear the flash.

Reading the build report

You do not need to understand every line yet. Click the lines you just saw to learn what they mean:

A LUT4 is a 4-input lookup table: the FPGA’s basic piece of combinational logic. In this report the whole design uses 47 of the chip’s 20,736 (a newer suite version reported 73: exact counts change with the tool version). This chip is big; this circuit is tiny.
D flip-flops. We have 25: the 24-bit counter cnt (CNT_W = $clog2(13,500,000) = 24) plus the 1-bit q. You can predict resource counts from your code; that skill matters later.
The Gowin fabric has dedicated carry-chain cells called ALUs. Yosys maps adders and counters like cnt + 1 onto them because they are fast and cheap.
I/O blocks are the pins you use: 1 clock input + 1 button input + 6 LED outputs = 8.
A global clock buffer. The clock is distributed through a dedicated low-skew network instead of ordinary routing; nextpnr inserted it for clk automatically.
Rows at zero are chip resources this design does not use: block RAM (BSRAM), hard multipliers (MULT18X18, the DSP blocks) and PLLs (rPLL). You will use all of them in later levels.
The timing report: the slowest path in the design could run with a clock up to ~390 MHz, and we only ask for 27 MHz, so there is a lot of margin. The line appears twice: the first is an estimate after placement, the last one is the final result after routing. In Level 2 you will learn to read and fix this line when it says FAIL.

Troubleshooting

Start with make doctor; it catches most setup problems.

SymptomLikely causeFix
make is not recognized / command not found GNU make is not installed, or the terminal was opened before installing it Windows: winget install ezwinports.make, then close and reopen VSCode. Linux: sudo apt install make. macOS: xcode-select --install.
make doctor says not found in the usual places, or yosys is not recognized Suite extracted somewhere unexpected (often one folder too deep) Find the folder that contains bin\yosys.exe and set the OSS_CAD_SUITE environment variable to it, or move it to C:\oss-cad-suite.
unable to open ftdi device: -3 (device not found) Board not seen: charge-only cable, loose connection, missing WinUSB driver, or board attached to WSL without usbipd Try another data cable/port; redo the Zadig step on interface 0 (Windows); redo the usbipd attach (WSL); check the udev rule (Linux).
It programs fine but nothing blinks Clock/LED pin wrong for your board revision, or the LED logic is inverted Confirm in constraints/tang_nano_20k.cst that clk is pin 4. Try driving all six LEDs low (assign led = '0;) to see which respond.
LED0 blinks only while S1 is held, or never blinks unless S1 is pressed The assumed button polarity is wrong for your board: the design sees the idle button as “pressed” In src/top.sv change BTN_PRESSED from 1'b1 to 1'b0, then make prog. Please report your result so the course can document it.
One or more LEDs never respond That LED’s pin number differs on your revision Compare the led[n] lines in the .cst with the board schematic from the Sipeed wiki.
The last Max frequency line says FAIL at 27.00 MHz The design cannot run at the requested clock Not expected for this design. You will learn to fix it in Level 2 (module 2.2).
Paths with spaces break the build Some tools mishandle spaces and synced folders Move the project to a short path such as C:\fpga\hello.
A warning about define gw2a not used Harmless message from this Yosys version Ignore it; the full log is in build/yosys.log.
The design builds, but the report shows LUT4: 0 and DFF: 0 and nothing blinks Yosys removed your logic because something it depends on is not driven (for example an input port left unconnected) Read the warnings printed by make build, such as Wire ... is used but has no driver, and connect every input of every module you instantiate.
